\chapter{Evaluation}\label{chapter:evaluation}

In the previous chapters, four common frameworks and their underlying 
algorithms were presented. To make an accurate and representative comparison, it is necessary to evaluate the 
accuracy of the distributions generated, as well as the performance of the algorithms used to generate them.

\begin{itemize}
    \item \textbf{Accuracy}: The statistical properties of the generated distributions will be compared to the expected values given by the theoretical Zipfian distribution
    \item \textbf{Performance}: The time taken to generate the distributions will be measured and compared using standard profiling tools as well as custom-written benchmarks
\end{itemize}

The variate generators considered were presented in the previous chapters: \ac{YCSB}, \ac{FIO}, Sysbench, and OLTP-Bench (which will not be further separated from YCSB), along with
implementations of the algorithms discussed in Chapter \ref{chapter:background}: Rejection and Condensed Table Lookup. Additionally, the \textit{Apache Commons} \cite{MathCommonsMath}
 implementation of the Rejection-inversion algorithm will be evaluated to compare it to its C counterpart.

\section{Methodology}
Three quantifiable criteria will be used to measure \textbf{accuracy} to offer a well-rounded view of the quality of the generated distributions - the \textbf{maximal absolute CDF difference} and the \textbf{sum of absolute PMF differences} as explained
previously in Chapter \ref{chapter:background}. They are well explored in the literature \cite{clausetPowerlawDistributionsEmpirical2009,leydoldErrorDetectionNonUniforma,dengRobustnessNonuniformRandom1992,monahanAccuracyRandomNumber1985}. 
Moreover, \textbf{frequency ratio graphs} will be used to evaluate accuracy through the whole \textit{support} of the distribution, allowing to observe biases related to the \textit{rank}.

The main measure of interest for \textbf{performance} is \textit{throughput} - the number of variates generated in a time interval (e.g. $10 \, \text{million} /ms$). However, measuring this quantity is
not trivial, as benchmarking in modern systems is unreliable if done inappropriately \cite{AvoidingBenchmarkingPitfalls,beyerBenchmarkingResourceMeasurement2015}. Some precautions 
are taken to avoid this, which will be explained later in Section \ref{subsec:microbench}.

There is a noticeable "staircase" effect happening with \textit{Approximative (C)} and \textit{Condensed Table Lookup (C++)}, though the first is more acute due to the non-linearity
of the \textit{y-axis}. The implementation were evaluated to investigate possible causes.

The \textit{Approximative (C)} approach uses the same algorithm as its counterpart in Java. What differs between both is the choice of hashing, in both cases posterior to the generation
of the variate according to the algorithm exposed by Gray \cite{grayQuicklyGeneratingBillionrecord1994}. This points to the choice of hasing function of the \textit{C} version, but a rigorous analysis requires a twofold approach: 
First, disable hashing and evaluate the resulting distribution. Secondly, exchange the hashing algorithm used, which is $32$-bit based (investigating the source code reveal it is from a \textit{lookup3} from the \textit{Jenkin's} family of hashing functions \cite{jenkinsLookup3}) 
for a $64$-bit version. While this approach goes in a promissing direction, it was not possible to verify it in this work and is left open.

As for the case of the condensed table lookup, the problems lies in precision limitations of the generated tables - it is limited to $2^{30}$, or rather $5 \cdot 10^9$. A cutoff implies the algorithm
 cannot compute $f_{theo}(k)$ that differs more than a factor of $10^{-9}$, such that many \textit{ranks} will be "stored" in the same index.  
Consequently, stretches of the \textit{ranks} in the x-axis will have the same probability, resulting in the lines seen. Such a mechanism explains
the "staircase" effect seen in Figure \ref{fig:pmf-graphs}. Morever, the absolute difference between consecutive $f_{theo}(k)$ decreases as $k$ increases, as can be observed by the "plateau" lines getting
longer. Currently, an alternative that avoids the "staircase" effect is not known, and further investigation was not possible.

\paragraph{Frequency ratio graphs} 
To further analyse how the accuracy varies with changing \textit{rank} of the \textit{empirical/generated} distributions, the \textbf{frequency ratio graph} was used. 
It consists of the \textit{rank} $k$ in the \textit{x-axis} and the ratio $\frac{f_{emp}(k)}{f_{theo}(k)}$ in the \textit{y-axis}. The graphs in Figure \ref{fig:ratio-graphs} show the 
results for the six variate generators. We notice some patterns: the implementations in graph B and F overestimate the first rank, such that $f_{emp}(k) > f_{theo}(k)$; and
graph C presents an angled striped pattern. A clear cause for the artifact seen in graph B and F could not be verified and is a direction of improvement for this thesis. 
The second pattern can be explained by same phenomenon found in the \textit{PMF} graph. As the rank $k$ and $f_{emp}(k)$ stays constant 
for long intervals, $f_{theo}(k)$ increases. Eventually $f_{emp}(k)$ changes and the process begins again.

\paragraph{Maximal absolute CDF difference} 
While the previous analysis helped identify and explain big divergences in the behavior of the generators, a more careful comparison should still be conducted. Using metrics and statistical test, 
it is possible to determine whether an algorithm is accurate up to $90\%$ certainty. The first such metric is  $D_n = \sup_x |P(x) - Q()|$, 
and it was calculated for each implementation, as seen in Table \ref{tab:ks-results}. We observe that the largest error of the \ac{CDF} of the Approximative (Java) implementation is about fourty times
bigger than the equivalent for the \textit{Rejection-Inversion} algorithm. This is expected, as the latter is an exact method. On the other hand, the \textit{Approximative (Java)} algorithm and the \textit{Condensed Table Lookup} 
have high error readings, which is expected given that they are \textit{approximative}. To account for the precise error readings is, however, beyond the scope of this work 
and requires a sofisticated mathematical analysis.

the \textit{Approximative (Java)} algorithm is not yet discarded.

\paragraph{Sum of probability differences} 
To offer a more holistic view of the possible biases in the variate generators, a second metric is introduced - $d_{TV}(P,Q) = \frac{1}{2} \sum_{x \in X} |P(x) - Q(x)|$. As the literature
does not directly suggest its usage as a test statistic \cite{lehmannLargeSampleOptimality2022}, an arbitrary limit $\epsilon = 0.01$ is chosen: up to $1\%$ of the probability mass of the empirical distribution $F_{emp}$ 
can deviate from the $F_{theo}$. Table \ref{tab:tvd-results} summarizes the results, which can be read as "The Rejection algorithm has 3\% difference in probability mass compared to the theoretical value". Using 
the $\epsilon$ criterium defined, we accept \textit{Approximative (Java)} and \textit{Rejection-Inversion (both)}.

\paragraph{Discussion of accuracy results} Considering both metrics, the \textit{Rejection-inversion} and \textit{Approximative (Java)} implementations will be accepted. The Condensed 
table lookup does not pass the test, but could be further investigated, as table lookups are quite fast \cite{marsagliaFastGenerationDiscrete2004}. It might seem to be the case 
that these requirements were very strict, since a $10^{-3}$ difference in the CDF might seen small. However, small deviations could cause significant increases in latency and an example
of the latency in memory accesses can help illustrate this point. Drawing from relevant literature \cite{pattersonComputerOrganizationDesign2013,TeachYourselfProgramming},
we have that \textit{L2 Cache} has a latency of around $4$ ns, whereas \textit{DRAM} can be approximate at around $100$ ns. Assuming that $95\%$ of accesses hit the cache and then 
$5\%$ go to the main memory, it is possible to calculate the expected latency for both the true $F_{theo}$ and a $F_{emp}$ with $d_{TV} = 0.1$. Let $L_{true}$ be the former and $L_{wrong}$ 
the latter:
 
\begin{equation}
    \tilde{L}_{true} = \mathop{\mathbb{E}}(L_{true}) = 0.95 \cdot 4 ns \, + 0.05 \cdot 100 ns = 8.8ns
\end{equation}

\begin{equation}
    \tilde{L}_{wrong} = \mathop{\mathbb{E}}(L_{wrong}) = 0.85 \cdot 4 ns \, + 0.15 \cdot 100 ns = 18.4ns
\end{equation}

This would create a relative error of $\frac{18.4 - 8.8}{8.8} =  109\%$, which is quite significant. An equivalent calculation for the $\epsilon = 0.01$ used in the analysis yields a relative
error of only $10\%$, which is much more acceptable. 

\section{Evaluating Performance}\label{subsec:microbench}
Measuring performance presents difficulties in modern hardware, as controlling for external factors outside of the segment of code being tested is nontrivial.  
To better isolate the \textit{code to test}, some techniques are applied \cite{AvoidingBenchmarkingPitfalls,beyerBenchmarkingResourceMeasurement2015,BenchmarkingTipsLLVM}, as exposed below:

\vspace{0.3cm}
\fbox{
    \centering
    \parbox{0.8\linewidth}{
        \begin{itemize}
            \item Set specific CPU core for the process generating samples
            \item Disable frequency scaling
            \item Disable turbo boost
            \item Fix the maximal amount of available memory
            \item Warm-up runs 
        \end{itemize}
    }
    \label{microbenchmarking-precautions}
}
\vspace{0.3cm}

The languages of interest are C++, C, and Java; therefore, the benchmarking tools are Google Benchmark \cite{GoogleBenchmarkMicrobenchmark} and JMH \cite{AvoidingBenchmarkingPitfalls}.
For the latter, some further precautions are required:

\begin{itemize}
    \item Use the \verb|Blackhole| object to consume the results of the computation
    \item Use the \verb|CompilerControl| annotation to avoid inlining
    \item Use the \verb|State| annotation to avoid dead code elimination
\end{itemize}

At last, it is important to define the runs. Since what is going to be measured is throughput, we define the duration of a single run to be 1 second. This will be repeated thirty times
and the average throughput will be calculated. Since the speed is invariant to \textit{support size} $N$ and \textit{skew} $\alpha$, these are kept at $10^8$ and $0.8$, respectively.

For Google Benchmark, the following command will be used to run the benchmarks (for more details on how to use the tool, see \cite{GoogleBenchmarkMicrobenchmark}):
\begin{lstlisting}
    ./benchmark --benchmark_repetitions=30 --benchmark_min_warmup_time=1.0
\end{lstlisting}

As a precaution for the sample generation not be optimized away, the function \verb|benchmark::DoNotOptimize| was used on the resulting variable. The
same procedure was reproduced for the JMH (more details on \cite{AvoidingBenchmarkingPitfalls,jenkovJMHJavaMicrobenchmark}), yielding the following command:
\begin{lstlisting}
    java -jar target/benchmarks.jar -bm thrpt -wi 10 -i 30 -f 1 -r 1
\end{lstlisting}

will not be explored further, which limits a rigorous conclusion. Regardless, this points towards the JVM being responsible for the difference in performance.
